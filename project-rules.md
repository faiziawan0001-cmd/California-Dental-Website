# Website Redesign — Project Rules (Safety, Workflow & Constraints)

## ROLE
You are redesigning the **frontend only** of an existing live website.
Visual/UX decisions (colors, typography, layout patterns, animations, style)
come from `design-system/MASTER.md` (and any page-specific override file in
`design-system/pages/`) generated by the UI/UX Pro Max skill — always defer
to that file for design choices. This file governs everything the design
skill does NOT cover: safety, backend preservation, SEO, CMS constraints,
and workflow.

**If this file and the design system file ever conflict on a non-visual
matter (e.g. a form field name, a URL), the rules in THIS file always win.**

---

## 🚫 HARD RULES — NEVER BREAK THESE

1. **Never modify backend logic, server code, database queries, or API routes.**
   Only touch HTML structure, CSS, static JS for UI behavior, and assets.
2. **Preserve every form field `name`/`id` attribute exactly.** Backend scripts
   depend on these to receive submitted data correctly.
3. **Preserve all API endpoint URLs, form `action` attributes, and payment
   gateway script tags (Stripe, PayPal, etc.) unchanged.**
4. **Preserve authentication-related code** (login forms, session/cookie
   handling, auth redirects) exactly as-is unless explicitly told otherwise.
5. **Preserve all existing page URLs, slugs, and route paths** — do not rename
   or restructure URLs. This protects SEO rankings.
6. **Preserve heading hierarchy semantics** (one `<h1>` per page, logical
   `<h2>`/`<h3>` nesting) even while restyling.
7. **Never delete or overwrite CMS template tags, shortcodes, PHP includes,
   or server-rendered placeholders** (e.g. WordPress loop code, Liquid tags,
   Django/Jinja template syntax). Work around them, not through them.
8. **Never remove or alter third-party tracking/analytics scripts** (Google
   Tag Manager, Meta Pixel, etc.) unless explicitly asked to.
9. **Always work in a local copy or staging branch.** Never edit files directly
   on the live production server.
10. **Before finishing, list every file changed and flag anything you were
    unsure about** rather than guessing on backend-adjacent code.

---

## SEO Preservation
- Keep all existing `<title>`, meta description, and canonical tags intact
  unless explicitly asked to improve them.
- Do not change URL structure.
- Preserve/improve structured data (schema.org markup) if present.
- Keep alt text and heading text keyword-relevant where it already was.

## CMS Compatibility
- Detect the CMS/platform in use (WordPress, Shopify, Wix, custom PHP, etc.)
  before making structural changes.
- Work within the platform's templating system — do not fight the platform
  or hardcode content that the CMS is meant to manage dynamically.
- Flag if a requested change requires a plugin/theme file vs. a page builder.

---

## ✅ WORKFLOW

1. Clone/inspect the current live site's rendered HTML, CSS, and JS.
2. Map all backend touchpoints (forms, APIs, auth, payment scripts, CMS tags)
   and document them in the client brief before writing any code.
3. Read `design-system/MASTER.md` (and page override, if present) for all
   visual/design decisions.
4. Redesign locally, verifying visually in-browser at each major step.
5. Test all forms, links, and interactive elements against the mapped
   backend touchpoints to confirm nothing broke.
6. Test across mobile/tablet/desktop breakpoints (375px, 768px, 1024px, 1440px).
7. Run the design skill's pre-delivery checklist plus a quick SEO sanity check
   before calling it done.
8. Summarize all changes made and flag any assumptions for human review
   before deployment to production.
